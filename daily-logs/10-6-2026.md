## The Anatomy of a Future

### The Future Itself
In Rust, an `async fn` or async block does not execute immediately. Instead, the compiler transforms the asynchronous block into a discrete value — a state machine that implements the `Future` trait. This state machine packages:

- The current suspension point (where execution was paused at an `.await`).
- All the localized environment state (variables, parameters, and references) needed to resume operation later.

### The Output
Every `Future` evaluates to a specific type once completion is achieved. This type is mapped to the associated type `type Output;` within the `Future` trait declaration.

## The Polling Architecture & The Waker Protocol

### Polling Mechanics
Futures are passive. They do not run in the background on their own; they must be repeatedly interrogated by an executor via the `poll` method:

```rust
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>
```

- `Poll::Ready(val)`: The work is complete; the final value is returned.
- `Poll::Pending`: The work is blocked on an external resource (I/O, timers, or thread signals). Execution yields control back to the thread.

### The Waker
To avoid wasteful CPU spinning, an executor will sleep when all current tasks return `Poll::Pending`. The `Waker` is the mechanism that signals the executor to wake up a specific task.

- When a resource becomes ready, `waker.wake()` is executed.
- This alerts the runtime executor to place this specific future back into the active run queue for another round of `poll()`.

## Building a Custom Oneshot Channel
To contextualize these low-level patterns, I built a low-level synchronized oneshot communication channel. A oneshot channel allows exactly one sender to transmit a single value to exactly one waiting receiver across distinct thread boundaries.

### Sender, Receiver, and Inner State Architecture
The architecture splits into three main segments:

- **Inner**: The core payload layer sitting on the heap, holding the shared state memory space.
- **Sender**: The production handle designed to write data into the payload layer.
- **Receiver**: The consumer handle designed to read data out of the payload layer and implement the `Future` trait.

```rust
struct Inner {
    value: Option<String>,
    waker: Option<Waker>,
}

struct Sender   { inner: Arc<Mutex<Inner>> }
struct Receiver { inner: Arc<Mutex<Inner>> }
```

### The Synchronization Sandwich: `Arc<Mutex<Inner>>`
- **Arc**: Atomic Reference Counting guarantees that both handles hold valid references to the same block of heap memory across different operating system threads.
- **Mutex**: Mutual Exclusion wraps the inner values to guard against parallel execution data races, ensuring that only one handle can alter or access `value` or `waker` at a given instant.

### Constructor and Value Transmission
- **`oneshot()` Constructor**: Instantiates the default inner memory state and uses `Arc::clone` to cleanly distribute pointers to both handles.
- **`Sender::send(self, value: String)`**: Takes ownership of `self` by value. This architecture guarantees the method can only be invoked exactly once, enforcing a compile-time oneshot contract. It locks the inner mutex, updates the state container with `Some(value)`, and checks for an active waker. If one is registered, `.take().wake()` is fired to resume execution.

## Driving Progress: Implementing `block_on`
A `Future` requires a driver to step it through execution to completion. I studied the construction of a basic `block_on` executor loop that encapsulates the thread-blocking mechanism:

- Loops continuously until the target future updates to `Poll::Ready`.
- Pairs a local thread-parking mechanism (`std::thread::park` / `unpark`) inside a custom `Waker` implementation to pause the host CPU thread safely while waiting for external signals.
