##  Chapter 10: Traits & Lifetimes

###  Defining Shared Behavior with Traits
* **Concept:** Traits are Rust's version of interfaces. They define functionality a particular type must have and can share with other types.
* **Usage:** Learned how to implement traits for custom `Structs` to guarantee specific behaviors, and how to use Trait Bounds to restrict generic functions.

###  Validating References with Lifetimes (The "Final Boss")
* **The Core Problem:** Preventing **Dangling Pointers**. The Rust compiler needs to mathematically prove that a reference (a map) will never outlive the data it points to (the house).
* **Lifetime Annotations (`<'a>`):** They don't change how long data lives; they just describe relationships. Applied the **"Shortest Straw" rule**, where the compiler limits the return value's lifespan to the shortest-lived input.
* **`'static` Lifetime:** Learned that this special lifetime means the data lives for the entire duration of the program (e.g., string literals baked into the binary, or data passed into multithreaded `thread::spawn` closures).

##  Chapter 11: Automated Testing

###  How to Write and Control Tests
* **Setup:** Tests are placed inside a `mod tests` block annotated with `#[cfg(test)]`, meaning they only compile during testing, saving production build size.
* **The Test Attribute:** Individual test functions are flagged with `#[test]`.
* **Assertions:** Used `assert_eq!(left, right)` to mathematically verify expected outcomes.
* **Output Capture:** Discovered that Rust hides `println!` output for passing tests. Learned to use `cargo test -- --nocapture` to force terminal output.

###  Test Organization
* **Unit Tests:** Testing individual modules and functions (e.g., writing a config parser test).
* **Integration Tests:** Setting up external tests to use the library exactly as an end-user would.

##  Chapter 12: An I/O Project (Building a CLI)

This chapter brought everything together. I built a `minigrep` tool and learned professional Rust architecture.

###  Accepting Command Line Arguments
* **`std::env::args`**: Captured terminal input using `env::args().collect::<Vec<String>>()`.
* **Index 0:** Learned that `args[0]` is always the path/name of the executable itself, while the actual user arguments start at index `1`.

### Reading a File
* **`std::fs::read_to_string`**: Opened and read text files into a single, massive Heap-allocated `String`.

###  Refactoring to Improve Modularity and Error Handling
* **Separation of Concerns:** Moved the argument parsing out of `main` into a dedicated `Config` struct. `main.rs` now acts only as the setup/manager, while `lib.rs` handles the business logic.
* **Associated Functions:** Wrote `impl Config { fn new() }` to create a standard constructor, moving away from loose tuples.
* **Ownership & `clone()`:** Used `.clone()` on the CLI arguments so the `Config` struct fully owns its data, bypassing lifetime headaches.
* **Clean Exits:** Used `.unwrap_or_else(|err| { ... })` and closures to intercept errors, print clean user-friendly messages, and gracefully shut down the program using `process::exit(1)` instead of letting Rust panic.
* **Dynamic Traits (`Box<dyn Error>`):** Used this wild-card error type in the `run` function to handle multiple potential error types (like I/O errors) cleanly using the `?` operator.

###  Adding Functionality with Test-Driven Development (TDD)
* **The Process:** 1) Write a failing test for a `search` function. 2) Write just enough code to make it pass. 3) Refactor.
* **Lifetimes in Action:** Applied `<'a>` lifetimes to the search function to guarantee the returned string slices lived exactly as long as the file contents being searched.

### Working with Environment Variables
* **`std::env::var`**: Added an `IGNORE_CASE` feature. The program now checks the Linux operating system environment to see if a specific variable is set before executing the search.

###  Redirecting Errors to Standard Error (`stderr`)
* **`eprintln!`:** Swapped standard `println!` macros for `eprintln!` when logging errors. This ensures that if a user redirects the program's output to a text file (using `>`), the errors still show up on the screen instead of being buried in the file.
